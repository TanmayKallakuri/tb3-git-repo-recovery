# SPEC: `git-repo-recovery`

One Terminal-Bench 3 task. A team's bare git repository sat on a failing
disk. The agent restores it so that every branch and tag exists again with
its original target and every object is intact. The verifier holds the
original repository. Status: locked 2026-10-29.

Design rules (from the TB3 rubric and the two earlier attempts):

- Two-paragraph instruction, end state only, human voice. The instruction
  says that nothing needs to be guessed and nothing outside the repository
  is available; it does not list the damage or the recovery sources.
- The agent cannot build a local oracle. Object ids are checksums, so a
  candidate repair can be checked, but the original refs and the content
  of damaged objects have to be derived from what remains. Difficulty is
  inference across the repository's own data, not a test matrix.
- Every lost item is recoverable by construction through exactly one
  intended path (section 3). The oracle (section 5) performs those
  recoveries from the damaged repository alone; it never reads the
  original.
- All or nothing: reward 1 only if every ref and every object is right.
- Tiny surface: one bare repository of a few hundred objects, a verifier
  of a few hundred lines, no corpus. Trials bounded by the agent's own
  reasoning, not by fuzzing.
- Nothing cyber: repository repair after hardware failure. Category
  Software, subcategory Systems.

## 1. The original repository (generated, deterministic)

`orbit`: a small Python command-line tool for scheduling periodic jobs
(fictional, about fifteen source files, a `docs/` directory, a
`tools/` directory). History generated by `scripts/gen-repo/generate.py`
with fixed dates, fixed author identities and fixed content, so the
original is bit-identical on every run (seeded choices only; no clocks).

- Three authors with `*.example` addresses: Mira Okafor, Dev Patel, Lena
  Fischer. Every commit has committer identical to author, including the
  timestamp (the team commits its own work; this is visible in every
  intact commit and is what makes patch-based reconstruction exact).
- About 150 commits from 2026-01 to 2026-09 on `main`, `develop`,
  `feature/retry-policy`, `feature/cache-warmup`, `hotfix/1.2.1`, with
  merges into `main` and `develop`. Realistic commit messages, small
  diffs, a handful of renames and deletions, one binary file (a PNG logo).
- Releases by `tools/release.sh` (committed in the tree): writes
  `VERSION` from `git describe --tags --always`, regenerates
  `docs/API.md` from the package docstrings with `tools/gen_api_docs.py`
  (deterministic), appends a dated entry to `CHANGELOG.md`, commits
  "Release vX.Y.Z", then tags. Between releases, maintenance commits that
  touch `VERSION` leave describe output like `v1.2.1-3-g<abbrev>` in it
  (the script is also run by `make dist`; the generator calls it for a few
  non-release commits so such strings exist).
- Tags: annotated `v1.0.0`, `v1.1.0`, `v1.2.0`, `v1.3.0` (tag objects with
  a one-line message and the tagger identity); lightweight `v1.2.1`,
  `v1.3.1`, `v0.9.0-rc1`.
- `docs/patches/0001-*.patch` to `0003-*.patch`: `git format-patch`
  output of three commits from the 1.2 cycle, committed later in one
  commit "Archive the 1.2 patch series from the list" (the project mails
  patches; the archive is the team's habit). Headers carry author, date
  and subject; bodies carry the full diffs.
- A remote `mirror` (`refs/remotes/mirror/*`) tracking `main`, `develop`
  and `feature/retry-policy`, pushed right before the failure, so those
  tracking refs equal the branch tips.
- Object storage as a repository that has been through two `git gc`-like
  repacks without pruning: `objects/pack/pack-A.pack` (objects up to
  commit ~100) and `objects/pack/pack-B.pack` (objects up to commit ~140,
  including every object of pack-A again), both with `.idx`; the last
  ~10 commits and their trees and blobs are loose. Reflogs under `logs/`
  for HEAD and every branch. `packed-refs` holds the tags (git packs tags only by default; packed
  branches would resolve to stale values instead of being lost); loose refs
  for the branches. `info/refs` and `objects/info/packs` are removed by the
  damage step: the stale server-info listing would name the lost refs.
  `HEAD` is `ref: refs/heads/main`. `config` has the mirror remote.

The generator writes the original to `tests/original/` (ground truth,
never in the agent image) and the damaged copy to
`environment/repo.git/`, plus `tests/expected-refs.txt` and
`tests/damage.json` (what was damaged and the intended recovery path, for
the write-up and the oracle's self-check; also never in the agent image).

## 2. The damaged repository the agent sees (`/app/repo.git`)

A bare repository. `git fsck --full` reports missing and corrupt objects;
`git log` on `main` works until it hits a damaged object; some branches
and tags are gone.

## 3. Damage classes and their one intended recovery path

| # | Damage | Count | Intended recovery | Skill |
|---|---|---|---|---|
| D1 | Entries in `pack-B.pack` with their compressed data overwritten by zeros (objects that also exist in `pack-A.pack`) | 20 (commits, trees, blobs mixed) | Read the intact copy from pack-A | pack inventory across packs |
| D2 | Entries in `pack-B.pack` that are the OFS_DELTA base of other pack-B entries, zeroed; the bases exist in pack-A; the dependent deltas are intact and exist only in pack-B | 3 bases, 6 dependents | Take the base from pack-A, apply pack-B's delta (format documented in git's `pack-format` and `pack-heuristics` docs) | pack delta format |
| D3 | Loose objects with one byte of the zlib stream altered | 6 (2 commits, 2 trees, 2 blobs) | The object id is known from the referencing object; try single-byte substitutions until inflate succeeds and the id matches | checksum-guided search |
| D4 | Objects of the three commits in the archived patch series, zeroed in pack-B with no copy in pack-A: the commit objects, the trees that changed and the blobs that changed | 3 commits, 6 trees (root and subtree per commit), 4 blobs | Apply each patch to its parent's tree; rebuild blob, tree and commit; author and date from the patch headers, committer = author as everywhere in the repository; the resulting ids match the parent links of later commits | reconstruction from a different representation |
| D5 | The `docs/API.md` blob of release v1.3.0, zeroed in pack-B, no copy in pack-A, not in any patch | 1 | Regenerate it with `tools/gen_api_docs.py` from that commit's tree (the tool is deterministic and its inputs are intact) | regenerating a generated artifact |
| D6 | `objects/pack/pack-A.idx` deleted | 1 | `git index-pack` recreates it | tooling |
| R1 | Loose `refs/heads/develop` and `refs/heads/feature/cache-warmup` deleted, their reflogs intact | 2 | Last reflog entry's new value | reflogs |
| R2 | `refs/heads/feature/retry-policy` and its reflog deleted | 1 | `refs/remotes/mirror/feature/retry-policy` | tracking refs |
| R3 | `packed-refs` truncated after `v1.1.0`: loses the annotated tags `v1.2.0` and `v1.3.0` and the lightweight tags `v1.2.1`, `v1.3.1`; the loose ref of `hotfix/1.2.1` deleted (its reflog intact) | 5 | Annotated tags: the dangling tag objects name their tag and target. `hotfix/1.2.1`: reflog. Lightweight tags: the release commit on the first-parent line of `main` (subject `Release vX.Y.Z`, `VERSION` exactly `vX.Y.Z`, the commit that introduces the `CHANGELOG.md` entry), pinned uniquely by a later `VERSION` string `vX.Y.Z-N-g<abbrev>`: only that commit is N commits behind `<abbrev>` | inference from the project's own release data |

`HEAD`, `config`, `logs/HEAD`, `refs/heads/main`, pack-B's `.idx`, and
every object not listed are intact. `v0.9.0-rc1` and `v1.0.0`, `v1.1.0`
survive in `packed-refs`. Nothing is damaged twice. Nothing requires
guessing: each item above has exactly one consistent answer, checkable by
the object ids that intact objects reference.

Sizing: about 650 objects in the original; about 45 damaged or lost
objects and 8 lost refs. An expert who knows git's object model, pack
format and plumbing needs about six hours.

## 4. Instruction (draft; Tanmay rewrites in his voice before push)

Paragraph 1: `/app/repo.git` is the bare repository of orbit, the team's
job scheduler, recovered from a failing disk. `git fsck` reports missing
and corrupt objects, several branches and tags are gone, and the last
backup is months old and useless. The repository was in normal use until
the failure: two repacks without pruning, reflogs on, a mirror remote
pushed moments before, releases cut by the project's own release script,
the patch series of the 1.2 cycle archived in the tree.

Paragraph 2: Repair the repository in place. When you are done,
`git fsck --full --strict` must report no missing or corrupt objects and
every branch and tag the repository had before the failure must exist
again, pointing at its original commit or tag object, with all of its
history and content intact. Nothing outside the repository is available
and nothing needs to be guessed: everything that was lost can be
reconstructed from what remains. Do not rewrite history, do not create
refs that did not exist, and leave the repository at `/app/repo.git`.

Then the mandatory suffix with N = agent timeout.

## 5. Oracle (`solution/`)

`solution/recover.py` (Python 3.12 standard library plus the `git`
binary) performs every recovery of section 3 from `/app/repo.git` alone:
inventories both packs (parsing pack-B around its zeroed entries), writes
intact copies from pack-A as loose objects, reconstructs the D2 dependents
by applying pack-B deltas to pack-A bases, searches single-byte
substitutions for D3, rebuilds the D4 objects from the patch files,
regenerates the D5 blob at the v1.3.0 tree, recreates pack-A's index,
restores the refs from reflogs, the mirror, the tag objects and the
describe strings, and finally runs `git fsck --full --strict`.
`solve.sh` runs it. It never reads `tests/`. It does not hardcode any
object id: every id it writes is derived from the repository.

## 6. Verifier (`tests/`, separate container)

Image: `python:3.12-slim-bookworm` (same digest as the agent image) plus
`git`, pytest and pytest-json-ctrf from a committed `uv.lock`; an
unprivileged user `checker` (uid 1700). `COPY . /tests/` with
`tests/original/` (the original bare repository as plain files),
`tests/expected-refs.txt` (`git for-each-ref --format='%(objectname) %(objecttype) %(refname) %(*objectname)' refs/heads refs/tags` of the original, sorted)
and `tests/expected-head.txt` (`ref: refs/heads/main`). Artifact:
`/app/repo.git/` (declared in task.toml).

Checks (pytest, one CTRF entry each, reward 1 iff all pass), all run on a
root-made copy of the artifact owned by `checker`, with git invoked as
`checker` with a fixed environment and `safe.directory` set:

1. `test_artifact_staged`: `/app/repo.git` is a bare repository (HEAD,
   objects/, refs/ present; `git rev-parse --is-bare-repository` true).
2. `test_fsck_clean`: `git fsck --full --strict --no-dangling` exits 0
   and prints no `missing`, `corrupt`, `error` or `broken` lines.
3. `test_refs_restored`: the sorted `for-each-ref` output over
   `refs/heads` and `refs/tags` equals `expected-refs.txt` exactly (same
   names, same ids, same peeled ids), and `HEAD` equals
   `expected-head.txt`.
4. `test_history_intact`: for every expected ref, `git rev-list --objects
   <id>` succeeds and every listed object passes `git cat-file -e`; the
   set of reachable object ids equals the original's reachable set.
5. `test_no_history_rewrite`: no ref under `refs/heads` or `refs/tags`
   that is not in the expected list (the mirror's tracking refs are not
   checked).

`reward-details.json` records fsck output, the ref diff, and the missing
or extra object ids. Verifier-side failures (git missing, copy failure)
exit 2 without a reward file.

### Cheat defences

- Object ids are SHA-1 of content: a fabricated object cannot carry a
  required id, and the expected ids are only in the verifier image.
- Refs pointing at ids whose objects are missing fail check 2 and 4.
- Deleting history fails check 4; adding refs fails check 5.
- git runs unprivileged on a copy; `/tests` and `/logs/verifier` are
  root-only.
