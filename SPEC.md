# SPEC: `git-repo-recovery`

One Terminal-Bench 3 task. A team's bare git repository sat on a failing
disk. The agent restores it so that every branch and tag exists again with
its original target and every object is intact. The verifier holds the
original repository. Status: revised 2026-10-30.

Design rules (from the TB3 rubric and the two earlier attempts):

- Two-paragraph instruction, end state only, human voice. The instruction
  says that nothing needs to be guessed and nothing outside the repository
  is available; it does not list the damage or the recovery sources.
- The local oracle is reduced, not removed: 2 of the 53 damage items (L1,
  L2) have no local oracle, and the object id still checks the other 51.
  Object ids are checksums, so a candidate repair of those can be checked,
  but the original refs and the content of damaged objects have to be
  derived from what remains. Difficulty is inference across the
  repository's own data, not a test matrix.
- Every lost item is recoverable by construction through exactly one
  intended path (section 3). The oracle (section 5) performs those
  recoveries from the damaged repository alone; it never reads the
  original.
- Oracle-free hardening (2026-10-30): two lost items (L1, L2) have exact
  bytes derivable from explicit evidence in the tree, but their ids appear
  nowhere in the repository, not even as a 7-hex prefix or in binary form.
  A wrong reconstruction of either passes fsck and every local check; only
  the hidden original catches it. Everything else stays locally checkable
  by hash, so the task cannot be solved by scanning for ids, and the
  generator asserts the no-leak property on every build.
- Sibling-pattern hardening (1.2.0): the conventions an agent can validate
  on surviving data (committer equals author on every other commit; the
  tagger line equals the release commit's committer line on the four
  surviving annotated tags; the archived series matches an existing chain
  byte for byte) give the wrong answer for L1 and L2. The tool that
  produced each, read as of the commit that ran it, states the right one
  in plain words, and the generator asserts that following the tool
  reproduces the bytes while following the sibling pattern does not.
- All or nothing: reward 1 only if every ref and every object is right.
- Tiny surface: one bare repository of a few hundred objects, a verifier
  of a few hundred lines, no corpus. Trials bounded by the agent's own
  reasoning, not by fuzzing.
- Nothing cyber: repository repair after hardware failure. Category
  Software, subcategory Systems.

## 1. The original repository (generated, deterministic)

`orbit`: a small Python command-line tool for scheduling periodic jobs
(fictional, about fifteen source files, a `docs/` directory, a
`tools/` directory). History generated by `scripts/gen-repo/generate.py`
with fixed dates, fixed author identities and fixed content, so the
original is bit-identical on every run (seeded choices only; no clocks).
About 161 commits from 2026-01 to 2026-10-15.

- Three authors with `*.example` addresses: Mira Okafor, Dev Patel, Lena
  Fischer. Every commit but two has committer identical to author,
  including the timestamp (the team commits its own work; this is visible
  in every intact commit and is what makes patch-based reconstruction
  exact). The two exceptions are the rebased pair of
  `feature/cache-warmup` (L1 below): committer Mira at Lena's author
  dates, time zone included, as `git rebase
  --committer-date-is-author-date` records them.
- Branches `main`, `develop`, `feature/retry-policy`,
  `feature/cache-warmup`, `hotfix/1.2.1`, with merges into `main` and
  `develop`. Realistic commit messages, small diffs, a handful of renames
  and deletions, one binary file (a PNG logo).
- Releases by `tools/release.sh` (committed in the tree): writes
  `VERSION` from `git describe --tags --always`, regenerates
  `docs/API.md` from the package docstrings with `tools/gen_api_docs.py`
  (deterministic), appends a dated entry to `CHANGELOG.md`, commits
  "Release vX.Y.Z", then tags. Between releases, maintenance commits that
  touch `VERSION` leave describe output like `v1.2.1-3-g<abbrev>` in it
  (the script is also run by `make dist`; the generator calls it for a few
  non-release commits so such strings exist). The script has three
  versions in the history: v1 (one-line tag message, `-l` for a
  lightweight tag, the tag made with the release commit's identity and
  date, the CHANGELOG heading `## vX.Y.Z - YYYY-MM-DD`), v2 (x.y.0
  releases get an annotated tag whose message is `orbit vX.Y.0`, a blank
  line and the bullet lines of that version's CHANGELOG section, tagged in
  the name of the release commit's committer and dated from
  `SOURCE_DATE_EPOCH`, which the script defaults to the committer time of
  the commit the release is cut from and writes into the heading as
  `## vX.Y.0 - YYYY-MM-DD HH:MM:SS +0000`; the tagger date is that time in
  +0000, which differs from the release commit's date and zone; everything
  else lightweight), v3 (back to a one-line message, same date rule; its
  commit body says the 1.4.0 tag carried the full notes). 1.4.0 is the
  only release cut with v2; HEAD has v3. A later commit on `develop`
  corrects one bullet of the 1.4.0 section, so HEAD's `CHANGELOG.md`
  differs from the release commit's.
- Tags: annotated `v1.0.0`, `v1.1.0`, `v1.2.0`, `v1.3.0` (tag objects with
  a one-line message and a tagger line equal to the release commit's
  committer line) and `v1.4.0` (v2 format, loose tag object, dated from
  the heading); lightweight `v1.2.1`, `v1.3.1`, `v0.9.0-rc1`.
- `docs/patches/0001-*.patch` to `0003-*.patch`: `git format-patch`
  output of three commits from the 1.2 cycle, committed later in one
  commit "Archive the 1.2 patch series from the list" (the project mails
  patches; the archive is the team's habit). Headers carry author, date
  and subject; bodies carry the full diffs. `docs/patches/cache-warmup/`:
  the two commits of `feature/cache-warmup` since its last merge, written
  by `tools/archive-series.sh`, which Mira ran on `develop` on the last
  day, after the last nightly push. The script rebases the branch onto
  the current HEAD with `git rebase --committer-date-is-author-date` (its
  header says in plain words that the runner becomes the committer and
  the author dates, time zone included, are kept), force-pushes it with a
  lease, exports `format-patch --no-thread --zero-commit --no-signature`
  of the rebased commits (so the From lines are all zeros) with a
  `series` file that names the branch the series was exported from and
  lists the patches in order, and commits the archive as the runner. The
  rebase is a clean replay (`orbit/cache.py` did not change on `develop`
  since the series base), so the pre-rebase pair by Lena, with committer
  equal to author, which the mirror still holds, matches both patches by
  author, date and subject and reproduces the archive byte for byte under
  the same `format-patch` flags.
- A remote `mirror` (`refs/remotes/mirror/*`) tracking every branch. A
  cron job pushes all branches to it at 02:00 UTC every night (documented
  in `docs/operations.md`; tags are not mirrored). The generator pushes at
  the first 02:00 boundary after each change, which is the state a real
  nightly leaves. The last day's three pushes (the archive run, which
  force-pushes the rebased `feature/cache-warmup` and pushes the archive
  commit on `develop`; a test; a merge) came after the last nightly, so
  `mirror/feature/cache-warmup` holds the pre-rebase pair (its reflog
  shows the two nightly pushes that brought it there) and `mirror/main`,
  `mirror/develop` lag their branches; `mirror/feature/retry-policy` and
  `mirror/hotfix/1.2.1` equal their tips.
- Object storage as a repository that has been through two `git gc`-like
  repacks without pruning: `objects/pack/pack-A.pack` (objects up to
  commit ~100) and `objects/pack/pack-B.pack` (objects up to commit ~140,
  including every object of pack-A again), both with `.idx`; the last
  ~20 commits with their trees and blobs and the v1.4.0 tag object are
  loose (every push stays under `transfer.unpackLimit`). Reflogs under
  `logs/` for HEAD, every branch and every mirror tracking ref
  (`core.logAllRefUpdates = true`, so tags have none). The timestamps up
  to the TAIL marker in `history.py` are frozen, so both packs and every
  object before the tail are byte-identical to the first release of the
  task (`scripts/gen-repo/frozen-victims.txt`, checked by `verify.sh`).
  The victims of D1, D2, D4, D5 and D6 are unchanged; D3 candidates are
  chosen among loose objects and include tail objects, so the D3 picks
  change between versions (the evidence files, the trees on their paths,
  the tips' root trees, the mirror's pair and the hidden objects are never
  candidates).
  `packed-refs` holds the tags up to v1.3.1 (git packs tags only by default; packed
  branches would resolve to stale values instead of being lost); loose refs
  for the branches. `info/refs` and `objects/info/packs` are removed by the
  damage step: the stale server-info listing would name the lost refs.
  `HEAD` is `ref: refs/heads/main`. `config` has the mirror remote.

The generator writes the original to `tests/original/` (ground truth,
never in the agent image) and the damaged copy to
`environment/repo.git/`, plus `tests/expected-refs.txt` and
`tests/damage.json` (what was damaged and the intended recovery path, for
the write-up; its reader is the verifier's preflight, which checks it
against the original; also never in the agent image).

## 2. The damaged repository the agent sees (`/app/repo.git`)

A bare repository. `git fsck --full` reports missing and corrupt objects;
`git log` on `main` works until it hits a damaged object; some branches
and tags are gone.

`HEAD`, `config`, `logs/HEAD`, `refs/heads/main`, pack-B's `.idx`, and

survive in `packed-refs`. Nothing is damaged twice. Nothing requires
guessing: each item above has exactly one consistent answer; for D1-D6
and R1-R3 the object ids that intact objects reference check it, for L1
and L2 the evidence in the tree determines the bytes and the generator
asserts that the reconstruction procedure reproduces them exactly, and
that the sibling patterns (committer = author on the rebase, the tagger
line equal to the release commit's committer line, HEAD's CHANGELOG
bullets) do not. The no-leak scan (damage.py, check_damage.py) asserts
that none of the seven hidden ids (the rebased pair, its four trees, the
tag object) appears in any file, path or other object's content of the
damaged repository, as a 7-hex prefix or in 20-byte binary form, and
`git fsck --full` of the damaged repository names none of them. With the
branch at the mirror's value and every other ref restored, fsck of the
original minus the hidden objects reports nothing: no dangling object
points at the loss.

Sizing: 619 reachable objects in the original; 53 damage items covering
51 damaged or lost objects (50 with an id: 43 locally checkable (D1 20,
D2 3, D3 6, D4 13, D5 1) plus 7 hidden (the six rebase objects and the
v1.4.0 tag), plus the pack-A index) and 9 lost refs. An
expert who knows git's object model, pack format and plumbing needs
about six hours.

## 4. Instruction

The exact text is `tasks/git-repo-recovery/instruction.md` (the canary
line aside):

> `/app/repo.git` is the bare repository of orbit, the job scheduler our team maintains, as it came off a failing disk. `git fsck` reports missing and corrupt objects, several branches and tags are gone, and the last backup is months old and useless. The repository was in normal use right up to the failure.
>
> Repair the repository in place. When you are done, `git fsck --full --strict` run in `/app/repo.git` must report no missing or corrupt objects, and every branch and tag the repository had before the failure must exist again, pointing at its original commit or tag object, with all of its history and content intact. Nothing outside the repository is available and nothing needs to be guessed: everything that was lost can be reconstructed from what remains. Do not rewrite history, do not create refs that did not exist, and leave the repository at `/app/repo.git`.
>
> You have 28800 seconds to complete this task. Do not cheat by using online solutions or hints specific to this task.

The witnesses, repacks, reflogs, the nightly mirror, the release script and
the archived series are not listed: finding them is part of the task.

## 5. Oracle (`solution/`)

`solution/recover.py` (Python 3.12 standard library plus the `git`
binary) performs every recovery of section 3 from `/app/repo.git` alone:
inventories both packs (parsing pack-B around its zeroed entries), writes
intact copies from pack-A as loose objects, reconstructs the D2 dependents
by applying pack-B deltas to pack-A bases, searches single-byte
substitutions for D3, rebuilds the D4 objects from the patch files,
regenerates the D5 blob at the v1.3.0 tree, recreates pack-A's index,
restores the refs in this order: dangling tag objects, reflogs,
lightweight release tags pinned by describe strings, the archived series
(each listed patch is matched to a commit by author, date and subject,
chained by parent; a patch matching nothing is rebuilt on the chain,
committer = author, and kept only when its tree already exists in the
repository; when every patch matches an existing chain but
`tools/archive-series.sh` as of the commit that introduced the series
file rebases before exporting, the chain is rebased in a `--shared`
scratch clone onto the archive commit's parent with
`--committer-date-is-author-date` as the archive commit's committer,
kept only when `format-patch --zero-commit --no-thread --no-signature`
of the result is byte-identical to the archive, its new objects moved
in; the branch is created at the resulting tip, so the mirror's stale
value is never used for it; a second run finds the branch at a chain
tip and does nothing), the mirror's tracking refs for what is still
missing, and the release replay (clone `--shared`, check out the parent
of an untagged release commit, run `tools/release.sh` as of that commit
with the commit's identity and date, `SOURCE_DATE_EPOCH` from the time
in the CHANGELOG heading as of that commit when it carries one and the
commit's time otherwise, keep the tag only when the replayed commit is
the original one, transfer the tag object with `hash-object -t tag
-w`); then `git fsck --full --strict`. `solve.sh` runs it. It never
reads `tests/`. It does not hardcode any object id: every id it writes
is derived from the repository, and for L1 and L2 no id exists to
compare against.

## 6. Verifier (`tests/`, separate container)

Image: `python:3.12-slim-bookworm` (same digest as the agent image) plus
`git`, pytest and pytest-json-ctrf from a committed `uv.lock`; an
unprivileged user `checker` (uid 1700). `COPY . /tests/` with
`tests/original/` (the original bare repository as plain files),
`tests/expected-refs.txt` (`git for-each-ref --format='%(objectname) %(objecttype) %(refname) %(*objectname)' refs/heads refs/tags` of the original, sorted)
and `tests/expected-head.txt` (`ref: refs/heads/main`). Artifact:
`/app/repo.git/` (declared in task.toml).

Staging and preflight. The verifier first makes a root-held staged copy of
the artifact and examines it before anything is cleaned or graded:

- The submitted `config` (at most 64 KiB) is parsed as the unprivileged
  `checker` with `git config --file <copy> --no-includes --list -z` and
  held to a denylist of settings that can redirect object or ref lookup,
  run a program or change the repository format: the sections
  `extensions`, `include`, `includeif`, `alias`, `credential`, `filter`,
  `uploadpack` and `gpg`, and any key whose final name is `program`,
  `command`, `driver`, `path`, `helper`, `hookspath`, `fsmonitor`,
  `sshcommand`, `gitproxy`, `askpass`, `alternaterefscommand`,
  `alternaterefsprefixes` or `worktree`. `core.repositoryformatversion`
  `0` and `core.bare` true are required. Every other setting (pager,
  editor, user, color, pack, gc, remotes and the like) is accepted,
  because grading never uses it: only after the check does the pinned
  grading config replace the submitted one. An unparseable config or a
  rejected setting fails `test_artifact_staged`. Up to 1.2.1 the check
  was an allowlist, which also rejected benign settings such as
  `core.pager`; 1.2.2 replaced it with this denylist.
- Symlinks and special files anywhere in the artifact reject it.
  Alternates, http-alternates, grafts, shallow and promisor markers reject
  it.
- A pure-Python ref inventory (`refs/` files and `packed-refs`, without
  git) is taken first; then `refs/replace` and the other indirections are
  removed from the grading copy. A name under `refs/replace/` still fails
  `test_no_history_rewrite`.
- A preflight checks that the original itself passes fsck and that the
  damage manifest `tests/damage.json` agrees with it: its 85 object ids
  exist in the original and its 9 lost refs are in `expected-refs.txt`.

Checks (pytest, one CTRF entry each, reward 1 iff all five pass), run on
the checker-owned copy, with git invoked as `checker` with a fixed
environment and `safe.directory` set:

1. `test_artifact_staged`: the copy is a bare repository (HEAD, objects/,
   refs/ present; `git rev-parse --is-bare-repository` true) and staging
   passed.
2. `test_fsck_clean`: `git fsck --full --strict --no-dangling` exits 0
   and prints no `missing`, `corrupt`, `error` or `broken` lines.
3. `test_refs_restored`: the sorted `for-each-ref` output over
   `refs/heads` and `refs/tags` equals `expected-refs.txt` exactly (same
   names, same ids, same peeled ids), and `HEAD` equals
   `expected-head.txt`.
4. `test_history_intact`: for every expected ref, `git rev-list --objects
   <id>` succeeds and every listed object passes `git cat-file -e`; the
   set of reachable object ids equals the original's reachable set.
5. `test_no_history_rewrite`: no ref name in any namespace that the
   original lacks, taken over git's listing and the on-disk inventory. A
   remote-tracking ref the original had and the artifact lacks is not a
   failure, because the instruction asks for branches and tags.

`reward-details.json` records fsck output, the ref diff, and the missing
or extra object ids. An error the artifact provokes (over-long names,
loops, collisions) is a graded failure with reward 0. A resource fault on
the verifier side (git missing, copy failure) is an infrastructure error:
exit 2 without a reward file.

### Cheat defences

- Object ids are SHA-1 of content: a fabricated object cannot carry a
  required id, and the expected ids are only in the verifier image.
- Refs pointing at ids whose objects are missing fail check 2 and 4.
- Deleting history fails check 4; adding refs in any namespace fails
  check 5.
- The submitted config cannot carry a hooks path, extensions, includes,
  aliases, helpers, program or command settings, or a non-bare setting
  past the denylist; symlinks, special files, alternates, grafts, shallow
  and promisor markers reject the artifact.
- git runs unprivileged on a copy; `/tests` and `/logs/verifier` are
  root-only.
